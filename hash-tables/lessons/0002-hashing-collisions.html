Hash tables · Lesson 2

Hashing, collisions, and the average O(1)

The exam’s remaining hash-table row is the complexity one: average-case insertion is O(1), with two named conditions and one named threat. This lesson explains what each piece means, then drills the row until the whole sentence comes out in one piece.

Why this lesson

Lesson 1 settled what a hash table is. Now comes the O(1) row, and the O(1) rule itself is from the Big O course - any constant-time operation is O(1) (see Lesson 1, the loop rules). This lesson attaches the two conditions and the threat to the row, so the exam’s sentence arrives whole.

The hash function: key to bucket

Behind the scenes the table is an array of buckets. The hash function turns the key into a number - the bucket position where that key’s pair will live:

hash("apple")   -> bucket 3
hash("banana")  -> bucket 7
hash("cherry")  -> bucket 7   (a collision, next section)

Two facts the exam assumes

The same key always maps to the same bucket. An effective hash function spreads keys evenly across buckets, so no bucket collects too many keys.

Collisions: two keys, one bucket

A collision happens when two different keys land in the same bucket - banana and cherry above. Both pairs are still stored; the table just has to resolve which is which, and that resolution costs extra work.

The exam’s threat, verbatim

Collisions can cause slower behavior in the worst case. A few collisions are normal and harmless. A table where everything collides loses the O(1) - which is exactly why the average case carries conditions.

The load factor: items to buckets

The load factor is the number of items divided by the number of buckets. A table with 100 buckets holding 50 items has a load factor of 50 / 100 = 0.5. As the factor climbs, buckets fill up and collisions multiply. A reasonably controlled load factor means the table grows - more buckets - before that happens.

The exam’s second condition, verbatim

The average case assumes an effective hash function and a reasonably controlled load factor. Effective hashing spreads keys; the controlled load factor keeps the spreading from being crowded out.

Why the average case is O(1)

Put the two conditions together. An effective hash function sends a new key to a bucket holding only a few keys, and the controlled load factor keeps it that way as the table grows. Storing the pair is then a fixed amount of work - compute the hash, drop the pair in its bucket - no matter how many items the table holds. Fixed work regardless of N is the Big O course’s definition of O(1).

The word “average” matters: on average, with those conditions, it is O(1). In a bad case - collisions piling up - it can be slower. The exam sentence says both halves; answer with both halves.
