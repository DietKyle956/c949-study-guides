Big O for Exams · Lesson 2

Recursion: count the levels

No loops to count. Instead, draw the recursion tree in your head and answer two questions: how many levels does it have, and how much work happens on each level? Multiply, and you are done.

Why this lesson

Recursion is the second thing exam writers reach for after loops, and it punishes guessing: the same-looking functions can be O(n), O(log n), O(n log n), or O(2ⁿ). The two questions below separate them mechanically. You will use the Lesson 1 skills - multiplying work and halving to a log - the whole way through.

The two questions

Every recursive call does some work, then calls itself on a smaller input. Picture the whole run as a tree of calls: the root is the first call, and its children are the calls it makes.

Question 1 - How many levels?

How many times can you shrink the input before the base case stops everything? Shrink by a constant amount (n − 1): n levels. Shrink by half (n / 2): log n levels. That is the same halving idea as the loops in Lesson 1.

Question 2 - How much work per level?

Add up the work of every call on one level. If each level does the same total work, then:

time = (work per level) × (number of levels)

This formula solves the four standard shapes below.

The four shapes that cover most exams

Shape 1 - One call, shrink by a constant: O(n)

def fact(n):
    if n <= 1: return 1
    return n * fact(n - 1)

n levels (n, n−1, ..., 1), one call per level, O(1) work each: n × O(1) = O(n).

Shape 2 - One call, shrink by half: O(log n)

def search(a, lo, hi, target):
    if lo > hi: return -1
    mid = (lo + hi) // 2
    if a[mid] == target: return mid
    if a[mid] < target: return search(a, mid+1, hi, target)
    return search(a, lo, mid-1, target)

The range halves on every call, so log n levels, one call each: O(log n). This is binary search.

Shape 3 - Split in half, combine costs O(n): O(n log n)

def merge_sort(a):
    if len(a) <= 1: return a
    mid = len(a) // 2
    left  = merge_sort(a[:mid])
    right = merge_sort(a[mid:])
    return merge(left, right)   # O(n) work

Two calls of half size, then O(n) work to merge. Level 1 does O(n), level 2 does O(n) across its two calls, level 3 does O(n) across its four calls... every level does O(n) total, and there are log n levels: O(n log n).

Shape 4 - Branching calls: O(2ⁿ)

def fib(n):
    if n <= 1: return n
    return fib(n - 1) + fib(n - 2)

Each call makes two more, so the number of calls roughly doubles every level, for n levels. Total calls grow like 2ⁿ: O(2ⁿ). Tower of Hanoi has the same shape.

The trap: doubling calls is not automatically exponential

def total(arr):
    if len(arr) == 0: return 0
    mid = len(arr) // 2
    return total(arr[:mid]) + total(arr[mid:])

Calls double each level, but the work per call halves at the same rate. Total calls: 1 + 2 + 4 + ... + n = 2n − 1 = O(n). What matters is calls × work per call across the whole tree, not how fast calls multiply.

Space: the stack

Every unfinished call holds a stack frame, so the space a recursion uses is its deepest chain of pending calls - the number of levels, not the total number of calls.

  • fact(n): O(n) stack - one chain n levels deep.
  • search: O(log n) stack - one chain log n deep.
  • fib(n): O(n) stack - the tree is huge, but the stack only ever holds one path down it.
  • merge_sort: O(n) - the scratch arrays it allocates, not the stack.
